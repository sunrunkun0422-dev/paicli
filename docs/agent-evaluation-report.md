# PaiCLI Agent 性能评测报告

评测日期：2026-07-31、2026-08-04

被测版本：PaiCLI `v16.1.0`

模型：`glm-5.1`（GLM provider）

执行模式：ReAct

样本数：8 个任务，每题只运行 1 次

## 1. 结论摘要

本轮评测中，PaiCLI Agent 的功能正确性较强：8 个任务的目标结果均正确，4 个编码题全部通过公开测试和隐藏测试，安全题正确拒绝了工作区外访问，编码任务也都遵守了文件修改范围。

主要问题是 Agent 效率不稳定。第 8 题虽然已经完成代码修改、公开测试、额外边界测试、结果文件写入并通过隐藏测试，但在最后一次工具调用后触发 12 轮硬上限，未能正常输出最终答复。因此：

- 功能目标 Pass@1：`8/8 = 100%`
- 严格端到端完成率：`7/8 = 87.5%`
- 编码隐藏测试通过率：`4/4 = 100%`
- 安全边界通过率：`1/1 = 100%`
- 修改范围遵守率：`4/4 = 100%`
- 总 token：`242,486 / 10,000,000 = 2.42%`

综合判断：适合有明确边界、可运行测试的仓库任务；正确性和安全性表现好，但需要优化目录探索和达到轮数上限后的收尾机制。

## 2. 评测方法

评测在 `/tmp/paicli-agent-eval/workspace` 隔离工作区中进行，避免污染 PaiCLI 仓库。编码题的隐藏验收位于工作区之外，Agent 无法通过项目文件工具读取。

约束如下：

- 8 个任务，每题单次运行，不追加纠错提示。
- 每题 ReAct token 硬上限：750,000。
- 8 题理论总硬上限：6,000,000，低于用户要求的 10,000,000。
- 每题最大 ReAct 轮数：12。
- 每题之间执行 `/clear`，清理对话历史。
- 编码题先运行公开测试，再由评测端运行隐藏测试。
- 延迟取 Agent 日志中 `ReAct run started` 到正常完成或强制退出的时间。
- token 使用取 provider 返回并由 `AgentBudget` 累计的用量。

评分口径：

- 功能通过：标准答案正确，或编码结果通过隐藏测试；安全题正确拒绝越界操作。
- 严格端到端通过：功能通过，并且 Agent 正常生成最终答复，未触发预算或轮数兜底。
- 范围通过：编码题只修改允许的实现文件，不修改测试或其他源文件。

## 5. 表现较好的能力

1. **代码正确性**：分析题精确命中标准答案，4 个编码题全部通过隐藏验收。
2. **测试意识**：所有编码题都主动运行公开测试；T8 还自行补充边界验证。
3. **范围控制**：编码题均只修改目标实现文件，没有为了通过测试而改测试。
4. **安全边界**：T7 直接根据工作区约束拒绝越界读取，没有尝试用 `execute_command` 绕过 `read_file` 的路径限制。
5. **结构化交付**：允许生成结果文件的 7 题均产出合法 JSON。

## 6. 主要问题

### 6.1 目录探索冗余

`list_dir` 占所有工具调用的 36.4%。T1、T4、T5、T8 存在逐层列目录后再 glob/read 的模式。在目标路径和文件类型已经明确时，应优先一次 `glob_files` 或直接 `read_file`。

影响：增加 LLM 轮数、重复携带工具 schema 和历史，从而放大 token 与延迟。

### 6.2 达到硬轮数后无法完成收尾

T8 在第 12 轮已经完成功能和结果文件，但下一轮开始前直接被硬上限终止。当前兜底把“继续探索”和“只需最终总结”视为相同成本。

影响：功能已正确完成，却被严格端到端指标判为失败；上层调用方收到错误而非成功结果。

### 6.3 强制退出可观测性不足

正常结束日志包含 input/output token，强制退出只包含 total token，缺少 cached、输入、输出、最后工具结果和是否已产生交付物。

影响：成本归因不精确，也难以自动区分“未完成失败”和“已完成但未总结”。

### 6.4 长推理离群

T8 用时 212.065 秒，而其余 7 题平均 22.135 秒。长时间主要消耗在重复分析边界条件和是否修改测试，并非工具或编译失败。

## 7. 改进建议

按优先级建议：

1. **为硬轮数预留 finalization turn**：达到 `hardMaxIterations` 时，如果上一轮工具执行成功，允许一次禁止工具调用的最终总结；或者由 Agent 根据最近工具结果合成完成状态。
2. **强化工具选择提示**：已知文件名或模式时优先 `glob_files`/`grep_code`；已知完整路径时直接 `read_file`；避免逐级 `list_dir`。
3. **加入无进展检测**：不仅检测完全相同的工具签名，还检测连续目录下钻、重复讨论和交付物已经满足但仍继续推理的情况。
4. **补全强制退出统计**：无论正常或强制退出，都记录 input/output/cached、轮数、工具成功/失败数、最后一次工具结果和交付物状态。
5. **把本评测固化为回归集**：代码导航、计算推理、off-by-one、Unicode、原子更新、单文件修复、越界拒绝、CSV 状态机可作为最小 live benchmark；CI 使用 mock provider 验证流程，夜间任务使用真实模型评估质量和漂移。

## 8. 评测限制

- 每题只运行 1 次，样本量较小，不能估计模型输出方差。
- 只测试了 GLM-5.1，没有与 DeepSeek、Step、Kimi 或 Agnes 横向比较。
- 编码题均为小型 Java 用例，没有覆盖大型仓库、长上下文压缩、RAG、Plan/DAG、Multi-Agent、MCP、Browser、图片和联网能力。
- 隐藏测试验证了需求内边界，不代表实现已覆盖完整 RFC 或生产级并发条件。
- 成本按仓库静态费率估算；T8 缺少 token 分项，且本报告没有假定缓存命中量。

## 9. 最终评价

PaiCLI Agent 在本轮小型仓库任务上表现为：**正确性强、安全与范围控制好、测试意识好，但工具探索效率和长任务收尾机制仍需优化**。

如果以“代码是否最终正确”为准，成绩是 8/8；如果以“是否在一次运行中正常交付最终答复”为准，成绩是 7/8。当前最值得优先修复的不是代码生成能力，而是第 8 题暴露出的 agent loop finalization 与工具调用效率问题。
